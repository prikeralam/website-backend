CORE / H

Users, Roles & Audit

The one authoritative user/role table (Module H) and the shared audit trail every other module writes to. workflow_status (draft → in_review → approved → published → unpublished) is reused as a plain CHECK constraint on every content-bearing table below, rather than its own table.

Built in apps/accounts 
erDiagram
    USERS_USER {
        bigint id PK
        string username
        string email
        string role "public | researcher | editor | fellow | admin"
        boolean is_active
    }
    ACCOUNTS_AUDITLOG {
        bigint id PK
        bigint actor_id FK
        string module
        string action
        string target
        jsonb metadata
        timestamptz timestamp
    }
    USERS_USER ||--o{ ACCOUNTS_AUDITLOG : "acted as"
MODULE A

Content Management System

Four workflow-gated content types feeding the Homepage and About PRI. Every table shares the same status / created_by / reviewed_by shape (Django's WorkflowMixin).

Built in apps/content

MODULE B

Publication Repository

Formal, versioned, citable research output — separate from Module A's simpler content blocks. Authors link to Module A's PersonProfile, not a duplicate author table.

Base fields built in apps/publications  ·  Versioning/tags/DOI are spec-only 
erDiagram
    PUBLICATIONS_PUBLICATION {
        bigint id PK
        string slug
        string title
        string format "report | working_paper | brief | explainer | infographic | video | data_story"
        string external_id "DOI or internal slug"
        string visibility "public | private"
        text_array tags
        string status
    }
    PUBLICATIONS_PUBLICATIONVERSION {
        bigint id PK
        bigint publication_id FK
        int version_number
        string file
        boolean is_current
        bigint uploaded_by_id FK
    }
    CONTENT_PERSONPROFILE {
        bigint id PK
        string name
    }
    PUBLICATIONS_PUBLICATION ||--o{ PUBLICATIONS_PUBLICATIONVERSION : "has versions"
    PUBLICATIONS_PUBLICATION }o--o{ CONTENT_PERSONPROFILE : "authored by"
    USERS_USER ||--o{ PUBLICATIONS_PUBLICATION : created_by
MODULE C

Data Repository & Dashboards

Built natively in Django — the earlier CKAN + Next.js/Prisma "Module C v0" plan is dropped. Three-tier visibility (public / on_request / internal_only) is enforced server-side; AccessRequest is the approve/deny queue for gated datasets.

Spec-only — no apps/datarepo app yet 
erDiagram
    DATAREPO_DATASET {
        bigint id PK
        string slug
        string format "csv | xlsx | geojson | spss"
        string theme
        string geography
        int year
        string visibility "public | on_request | internal_only"
        string status
    }
    DATAREPO_DASHBOARD {
        bigint id PK
        string slug
        string embed_type "datawrapper | tableau | d3"
        string theme
        string status
    }
    DATAREPO_ACCESSREQUEST {
        bigint id PK
        bigint user_id FK
        bigint dataset_id FK
        string status "pending | approved | denied"
        timestamptz requested_at
    }
    DATAREPO_DATASET }o--o{ DATAREPO_DASHBOARD : "shown in"
    DATAREPO_DATASET ||--o{ DATAREPO_ACCESSREQUEST : gates
    USERS_USER ||--o{ DATAREPO_ACCESSREQUEST : requests
    USERS_USER ||--o{ DATAREPO_DATASET : created_by
Visibility tierBehavior
publicListed, previewable, downloadable by anyone.
on_requestListed with metadata; download requires an approved AccessRequest for that user.
internal_onlyExcluded entirely from any non-staff response — not just download-gated.
MODULE D

Fellowship & Internship

Configurable per-program application forms, a review pipeline, and a one-way sync into Module A's PersonProfile at onboarding. The "Reviewer" role is modeled as an annotation on top of the five base roles (Module H's pattern), not a sixth global role.

MODULE E

Media Watch & Rapid Response

A case only reaches the public API once status = public — which requires both a confirmed classification and a published Response. That two-part gate is the module's core correctness guarantee.

Spec-only — future phase 
erDiagram
    MEDIAWATCH_MEDIACASE {
        bigint id PK
        string item_type "image | text | video"
        string classification "hate_speech | misinformation | communal_bias | other"
        string status "flagged | under_review | confirmed | public"
        bigint flagged_by_id FK
        bigint reviewed_by_id FK
    }
    MEDIAWATCH_RESPONSE {
        bigint id PK
        bigint case_id FK
        string type "rebuttal | op_ed | explainer | press_statement | toolkit"
        bigint published_by_id FK
        timestamptz published_at
    }
    MEDIAWATCH_MEDIACASE ||--o{ MEDIAWATCH_RESPONSE : "answered by"
    USERS_USER ||--o{ MEDIAWATCH_MEDIACASE : flags
    USERS_USER ||--o{ MEDIAWATCH_RESPONSE : publishes
MODULE F

Donor & Fundraising

Money flows one way: a Donation only becomes succeeded from an authenticated payment-gateway webhook, never a client call — and a TaxReceipt is generated only from a genuinely succeeded donation.

MODULE G

Forms, Surveys & Contact

One generic engine, many form instances — newsletter, volunteer, event registration, whistleblower, etc. are all FormDefinition rows, not separate tables. anonymous_allowed forms leave submitter_* columns null at write time, not merely hidden later.

Spec-only — future phase 
erDiagram
    FORMS_FORMDEFINITION {
        bigint id PK
        string slug
        jsonb field_schema
        jsonb routing_rule
        boolean anonymous_allowed
    }
    FORMS_FORMSUBMISSION {
        bigint id PK
        bigint form_id FK
        jsonb data
        boolean is_anonymous
        string submitter_email "null when anonymous"
    }
    FORMS_FORMDEFINITION ||--o{ FORMS_FORMSUBMISSION : collects
